3. Confirmed via `grep` that no other real secret value exists in any tracked or new file.

**⚠️ Action needed — this is not fixed on the live site yet.** `.vercelignore` only changes *future* deployments. The current production deployment still serves those `.md` files until this change is pushed and redeployed. Redeploy promptly.

### A3. Auth & sessions
- ✅ **Done** — Every protected route checks the session server-side. `api/_lib/requireSession.js` verifies the httpOnly cookie's HMAC signature and expiry before any handler logic runs, and writes its own 401 on failure — confirmed by direct handler tests: calling `/api/admin/password` and `/api/test/clients` with no cookie returns 401 *before* the Supabase call ever fires (verified by running each handler against a mock request with no env vars configured — they failed at the auth check, not a Supabase error).
- ✅ **Done** — Session cookies set `httpOnly`, `secure` (conditional on `x-forwarded-proto: https`, which Vercel always sets in production), and `SameSite=Strict`. Verified in `api/unlock.js` / `api/_lib/cookies.js` and by a direct assertion that the serialized cookie string contains all three flags.
- ➖ **Not applicable** — "login errors don't reveal whether an email exists" — there's no email/identity concept here, only a single shared password.
- ✅ **Done** — Rate limiting on the unlock endpoint: 8 attempts per 10 minutes per hashed IP, enforced in `api/unlock.js` via a Supabase-backed counter, checked *before* the expensive password-verification step.
- ✅ **Done (by design)** — Account lockout is deliberately *not* used as the brute-force defense (which the checklist warns can itself become a DoS vector); rate limiting is used instead, and it's time-bounded/self-clearing (a 10-minute sliding window), not a manual-unlock lockout.
- ✅ **Done** — The real gate is server-side: Supabase RLS is enabled with zero policies on every table (deny-by-default to `anon`/`authenticated`; only the server-only `service_role` key can read/write), and every protected API route independently re-verifies the session cookie rather than trusting a client-reported "unlocked" flag.
- ✅ **Done** — This project rolls its own password auth (not Supabase Auth), which the checklist explicitly flags as needing slow, salted hashing. Verified: `api/_lib/crypto.js` uses `crypto.scryptSync` (a slow, memory-hard KDF) with a random 16-byte salt per password, compared with `crypto.timingSafeEqual`. Unit-tested directly: correct password verifies, wrong password rejected, two hashes of the same password differ (confirming per-hash random salting).
- ❌ **Gap (Recommended)** — `portfolio/index.html` (the personal-portfolio subsite the "locked" gallery card points to) has **no server-side enforcement of its own** — it's an ordinary static file, reachable directly by URL regardless of session state, same as before this change. The click-through gate on the gallery card is real (it prompts for the password via the new server-backed flow before navigating), but a visitor who already knows or guesses the URL bypasses it entirely. This is a pre-existing property, not something this change introduced or regressed, and the content behind it (Zane's own public portfolio) is low-sensitivity — but it means the "password" doesn't uniformly gate everything it visually appears to gate. Closing this fully would need Vercel Edge Middleware intercepting `/portfolio/*` and checking the session cookie before serving the static file — a meaningfully larger change I did not make unprompted. Flagging for a decision, not silently leaving it.

### A3a. CSRF protection
- ✅ **Done** — `SameSite=Strict` is the primary defense here (not a Next.js project, so the Server-Action-specific notes don't apply). Strict mode means the browser never attaches `wc_session` to any cross-site request — form or fetch — so a forged cross-site POST to `/api/admin/password` or `/api/unlock` arrives with no valid session regardless of what it contains.
- ✅ **Done** — Every state-changing endpoint (`/api/unlock`, `/api/lock`, `/api/admin/password`) is POST-only; GET is rejected with 405 on all of them (verified by direct handler test). No state change is reachable via GET.
